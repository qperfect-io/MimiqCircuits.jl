Qubit Loss on MIMIQ

MIMIQ supports explicit qubit loss for simulations where a physical qubit may leave the computational space instead of only accumulating ordinary gate or measurement noise. This is useful when testing quantum algorithms against more realistic near-term hardware behavior, especially in workflows where missing qubits should change the later circuit execution.

In the Julia API, loss can be represented directly in a circuit. You can insert loss events, reload a lost qubit, write its loss status into classical bits, and rewrite partially affected instructions with a LossModel.

Loss can also be part of a custom Kraus channel. A Kraus channel becomes loss-aware when one or more branches are tagged with LossyOperator, which lets the channel separate survival branches from branches that lose a qubit.

Summary of Loss Functionality

Loss operations: Loss, Reload, Check, MeasureCheck.

Loss processing: sample_losses draws the random loss events, lower_losses rewrites loss into primitives, and resolve_losses does both and is the usual entry point. Use sample_loss_scenario to force a specific set of loss sites.

Loss-model rules: DropRule, ReplaceRule, DecorateRule, CustomRule, applied to one instruction by lossmodel_rewrite.

Loss markers: Lost and Reloaded are passive annotations that record where loss landed in a resolved circuit.

Loss-aware Kraus: LossyOperator branches inside Kraus, inspected with hasloss, lossoperators, survivaloperators, and losseffect. The lost qubits of a branch are given by lossyqubits and lossytargets.

Lossy mixed unitaries: MixedUnitary branches marked with the lossy keyword, detected with haslossybranch.

Loss operations

Loss in MIMIQ is represented explicitly in the circuit. You can add operations that mark a qubit as lost, reload a lost qubit, or query whether a qubit is still present.

Losing a qubit

Loss represents a loss event: at that point in the circuit the qubit is lost with probability p. Loss() is Loss(1.0), a certain loss.

using MimiqCircuits

c = Circuit()
push!(c, Loss(0.1), 1)
1-qubit circuit with 1 instruction:
└── Loss(0.1) @ q[1]

The probability may also be symbolic, but it must be numeric before the loss is resolved.

Once a qubit is lost, later instructions touching that qubit are dropped while resolving, until the qubit is reloaded.

Reloading a lost qubit

Reload makes a qubit available again. It always re-initialises the qubit to $|0\rangle$, whether or not it was lost, so later operations can use it.

c = Circuit()
push!(c, Loss(), 1)
push!(c, Reload(), 1)
push!(c, GateX(), 1)
1-qubit circuit with 3 instructions:
├── Loss(1.0) @ q[1]
├── Reload @ q[1]
└── X @ q[1]

Checking for loss

MIMIQ provides two operations to query the loss status of a qubit.

Check writes one classical bit:

  • 1 if the qubit is present
  • 0 if the qubit is lost

It does not touch the quantum state.

c = Circuit()
push!(c, Check(), 1, 1)
1-qubit, 1-bit circuit with 1 instruction:
└── Check @ q[1], c[1]

MeasureCheck measures the qubit if it is present and reports whether it is still present.

c = Circuit()
push!(c, MeasureCheck(), 1, 1, 2)
1-qubit, 2-bit circuit with 1 instruction:
└── MeasureCheck @ q[1], c[1:2]

The first classical bit stores the measurement result (0 if the qubit is lost), and the second classical bit stores the loss status.

Resolving loss

A circuit that contains loss operations is not yet runnable: the random events must be drawn and every loss operation rewritten into ordinary primitives. resolve_losses does this in one step. It first draws each Loss, then lowers the result into Reset, Measure, SetBit0 and SetBit1, plus passive Lost and Reloaded markers. The returned circuit contains no loss operations.

The rng keyword is a random number generator, used only to make the random loss samples reproducible. Omit it if you do not need the same result every time.

using Random

rng = MersenneTwister(42)

c = Circuit()
push!(c, Loss(0.2), 1)
push!(c, GateH(), 1)
push!(c, Check(), 1, 1)

resolve_losses(c; rng=rng)
1-qubit, 1-bit circuit with 2 instructions:
├── H @ q[1]
└── c[1] = 1

The basic behavior while resolving is:

  • Loss is drawn; a loss that fires emits a Lost marker
  • Reload becomes a Reset plus a Reloaded marker
  • Check and MeasureCheck become SetBit0 or SetBit1 (and a Measure for a MeasureCheck on a present qubit)
  • a Measure on a lost qubit becomes SetBit0, so a lost qubit reads 0
  • instructions acting only on lost qubits are dropped

If an instruction touches some lost qubits but not all of them, resolving consults a LossModel.

If you need the two halves separately, sample_losses returns a circuit with the random events drawn but the loss bookkeeping still present, and lower_losses lowers an already-sampled circuit into primitives.

Forcing a loss scenario

To study a specific outcome, sample_loss_scenario forces the chosen Loss sites, counted in circuit order, to fire, and resolves the others as not lost.

c = Circuit()
push!(c, Loss(0.2), 1)
push!(c, GateCX(), 1, 2)
push!(c, Loss(0.4), 2)

sample_loss_scenario(c, 2)
2-qubit circuit with 2 instructions:
├── CX @ q[1], q[2]
└── Lost @ q[2]

Loss models

Why Loss Models Exist

A LossModel is the user-defined policy used while resolving loss when an instruction is only partially affected. This happens, for example, when a two-qubit gate is scheduled but one of its qubits has already been lost while the other one is still present.

MIMIQ can detect this situation, but it should not guess the physics for the remaining qubits. Different hardware models and approximations can lead to different choices: drop the instruction entirely, apply a one-qubit error channel to each surviving qubit, keep a side-effect before or after the attempted operation, or generate custom replacement instructions. A LossModel is where you specify that choice explicitly.

If no rule is provided, MIMIQ uses the conservative behavior and drops instructions that touch lost qubits. Add rules when your hardware model or simulation workflow has a more specific response to partial loss.

When rules are used

While resolving, MIMIQ tracks which qubits are currently lost and rewrites the circuit as follows:

  • If an instruction touches no lost qubits, it is kept unchanged.
  • If an instruction touches only lost qubits, it is dropped.
  • If an instruction touches both lost and surviving qubits, the LossModel is consulted.
  • If no rule in the model matches, the instruction is dropped.

Rules are evaluated by priority and then by insertion order. A DropRule has higher priority than replacement or decoration rules, so it can be used to exclude specific operations before a broader salvage rule is applied. Once a rule matches, MIMIQ builds the rule's output and filters out any generated instruction that still touches a lost qubit.

This last filtering step is important. A one-qubit replacement such as Depolarizing1(0.2) is broadcast to the targets of the matched gate, and the copies on lost qubits are removed. A multi-qubit replacement that still touches a lost qubit is removed entirely.

You can create an empty model and add rules to it:

model = LossModel(; name="My Loss Model")
LossModel (My Loss Model, 0 rules)

The helper functions are:

  • add_drop!
  • add_replace!
  • add_decorate!

Replacing a partially lost gate

Use ReplaceRule when the original instruction should be removed and replaced by another operation on the surviving qubits. In this example, a CX whose target qubit has been lost is replaced by a one-qubit depolarizing channel on the remaining control qubit.

c = Circuit()
push!(c, Loss(), 2)
push!(c, GateCX(), 1, 2)

model = LossModel()
add_replace!(model, GateCX() => Depolarizing1(0.2))

resolve_losses(c; lossmodel=model)
2-qubit circuit with 2 instructions:
├── Lost @ q[2]
└── Depolarizing(1,0.2) @ q[1]

If the lost qubit is the control instead, the same rule keeps the replacement on the surviving target qubit.

c = Circuit()
push!(c, Loss(), 1)
push!(c, GateCX(), 1, 2)

resolve_losses(c; lossmodel=model)
2-qubit circuit with 2 instructions:
├── Lost @ q[1]
└── Depolarizing(1,0.2) @ q[2]

Drop rules

DropRule removes matching instructions when they touch lost qubits. Use this when a partially affected operation should not be salvaged. A DropRule without an operation is a catch-all rule.

model = LossModel()
add_drop!(model, GateSWAP())
LossModel (unnamed, 1 rules)
└── DropRule(GateSWAP())

Because drop rules have higher priority, they can override broader replacement rules:

model = LossModel([
    ReplaceRule(GateSWAP(), GateX()),
    DropRule(GateSWAP()),
])
LossModel (unnamed, 2 rules)
├── DropRule(GateSWAP())
└── ReplaceRule(GateSWAP() => GateX())

Decorating a partially lost gate

DecorateRule adds another operation before or after the matched instruction. While resolving, generated instructions touching lost qubits are filtered out, so if the original gate still touches a lost qubit it is removed and only surviving decorations remain.

model = LossModel()
add_decorate!(model, GateCZ() => Depolarizing1(0.01); before=true)
LossModel (unnamed, 1 rules)
└── DecorateRule(GateCZ(), Depolarizing(1, 0.01), before)

Use decoration when your model says that the attempted operation still causes a side effect, such as a local error channel on the qubits that were present.

Custom rules

Use CustomRule when the rewrite depends on more than the operation type. The generator receives the matched instruction and the current loss map. It may return nothing to drop the instruction, one Instruction, or a vector of instructions.

In Julia, the custom generator should also accept the keyword rng. This is the same random number generator passed to resolve_losses. Include it even if the rule does not need randomness.

c = Circuit()
push!(c, Loss(), 2)
push!(c, GateCX(), 1, 2)

model = LossModel([
    CustomRule(
        inst -> getoperation(inst) isa GateCX,
        (inst, lost; rng=nothing) -> [
            Instruction(GateZ(), q)
            for q in getqubits(inst)
            if !get(lost, q, false)
        ],
    ),
])

resolve_losses(c; lossmodel=model)
2-qubit circuit with 2 instructions:
├── Lost @ q[2]
└── Z @ q[1]

Applying a model to one instruction

lossmodel_rewrite applies a model to a single instruction, given a dictionary that says which qubits are lost. It returns the instructions that replace it, after removing those that touch a lost qubit. This is the step lower_losses performs for each partially lost instruction, and is useful to check what a model does before resolving a whole circuit.

model = LossModel()
add_replace!(model, GateCX() => Depolarizing1(0.2))

# qubit 2 is lost, qubit 1 is present
lossmodel_rewrite(Instruction(GateCX(), 1, 2), Dict(1 => false, 2 => true), model; rng=nothing)
1-element Vector{Instruction}:
 Depolarizing(1,0.2) @ q[1]

An empty vector means that the instruction is dropped, as happens when no rule matches:

lossmodel_rewrite(Instruction(GateCX(), 1, 2), Dict(2 => true), LossModel(); rng=nothing)
Instruction[]

The rng keyword is required, and is passed on to the generator of a CustomRule.

For most workflows, prefer DropRule, ReplaceRule, or DecorateRule because those rules are simpler to inspect and serialize. CustomRule is the escape hatch for policies that cannot be expressed with the built-in rule types.

Loss-aware Kraus channels

Custom Kraus channels can also model loss. A Kraus channel becomes loss-aware when one or more of its branches are tagged with LossyOperator.

k = Kraus([
    [1 0; 0 sqrt(0.9)],
    LossyOperator([0 sqrt(0.1); 0 0]),
])
Kraus(Operator([1.0 0.0; 0.0 0.948683…]), LossyOperator(0.0,0.0,0.316228…,0.0;lossy=(1,)))

You can inspect such channels using:

hasloss(k)
true
lossoperators(k)
1-element Vector{AbstractOperator}:
 LossyOperator(0.0, 0.0, 0.31622776601683794, 0.0; lossy=(1,))
survivaloperators(k)
1-element Vector{AbstractOperator}:
 Operator([1.0 0.0; 0.0 0.9486832980505138])
losseffect(k)
1-qubit Operator:
├── 0.0 0.0
└── 0.0 0.1

losseffect returns the operator describing the total loss probability carried by the lossy branches.

A LossyOperator records which of its qubits are lost when its branch is selected. lossyqubits returns them in the operator's own 1:N numbering, and lossytargets translates them to the qubits of the instruction the operator is applied to:

# a 2-qubit branch that loses its second qubit
op = LossyOperator(zeros(4, 4), 2)

lossyqubits(op)
(2,)
# applied to qubits 3 and 7, the branch loses qubit 7
lossytargets(op, (3, 7))
(7,)

Lossy mixed unitaries

A MixedUnitary channel can also lose qubits. The lossy keyword lists, for each branch, the qubits it loses; an empty list keeps the branch lossless. haslossybranch tells whether any branch loses qubits.

# with probability 0.1, apply X and lose the qubit
mu = MixedUnitary([0.9, 0.1], [GateID(), GateX()]; lossy=[Int[], [1]])

haslossybranch(mu)
true

When sample_mixedunitaries draws a lossy branch, it adds a Loss on the lost qubits after the branch's gate, which resolve_losses then processes as usual.

c = Circuit()
push!(c, mu, 1)
push!(c, GateH(), 1)

# with this seed the lossy branch is drawn
sample_mixedunitaries(c; rng=MersenneTwister(17))
1-qubit circuit with 3 instructions:
├── X @ q[1]
├── Loss(1.0) @ q[1]
└── H @ q[1]

If you only need the general Kraus formalism, see the Kraus operators section.
